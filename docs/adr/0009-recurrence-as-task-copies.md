# 0009. Повторения как копии задач

### Дата
2026-09-22

### Статус
Принято

### Контекст
У повторяющейся задачи есть два способа представления. Первый — одна запись, у которой при
выполнении дата сдвигается на следующее вхождение. Второй — порождение отдельной копии на каждое
вхождение. От выбора зависит история выполнений, поведение пропусков и сложность синхронизации.

### Решение
На каждое вхождение создаётся копия задачи. Копии одной серии связаны nullable-полем seriesId;
у одноразовых задач оно null. Пропущенные вхождения порождают по копии на каждую пропущенную дату
со статусом Skipped — неделя без запуска приложения даёт семь копий. Следующее вхождение считается
от dueDate, а не от момента выполнения.

### Последствия
История сохраняется: видно, какие вхождения выполнены, какие пропущены и когда. Каждое вхождение
можно отредактировать независимо — перенести, дописать подзадачи. Запросы к списку не нуждаются
в вычислении дат на лету. Количество строк растёт линейно со временем, у ежедневной задачи
за год это 365 записей. Синхронизация усложняется: вместо одного изменённого поля на сервер едут
новые сущности, и устройства, сгенерировавшие один и тот же пропуск независимо, дадут дубли —
дедупликация по паре seriesId и даты вхождения обязательна.

### Рассмотренные альтернативы
Сдвиг dueDate у одной записи — проще в синхронизации и экономнее по строкам, но история теряется
целиком, пропуски не выражаются, а правка одного вхождения невозможна без порождения копии,
то есть всё равно приводит к этой же модели, только частично.
