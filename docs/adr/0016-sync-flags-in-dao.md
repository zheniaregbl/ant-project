# 0016. Бамп updatedAt и isDirty в DAO-запросах

### Дата
2026-11-02

### Статус
Принято

### Контекст
Каждая строка несёт служебные поля синхронизации: updatedAt и isDirty. Их нужно обновлять при любой
локальной мутации. Делать это можно в DAO-запросе, в репозитории или в use case.

### Решение
Бамп выполняется в DAO-запросах, явным перечислением полей в UPDATE. Текущее время передаётся
параметром :now снаружи, а не вычисляется в SQL через strftime, чтобы в тестах подставлялся
фейковый Clock. Мутация подзадачи или тега бампает родительскую задачу в той же транзакции,
потому что эти сущности едут на сервер внутри задачи, а не отдельно.

### Последствия
Статус и служебные поля меняются одним запросом, без чтения сущности в память, атомарность
обеспечивается самим SQL. Бамп детерминирован и покрывается тестом. Главное последствие проявится
на фазе синхронизации: применение серверных данных при pull пойдёт через тот же DAO и будет
помечено грязным, что даст цикл — скачали, пометили, отправили обратно, скачали. Потребуется
отдельный путь, не трогающий флаги: либо второй набор методов с @Upsert, либо перенос бампа
в репозиторий, где локальный путь и применение серверных данных разделены явно. Решение отложено
до фазы бэкенда, чтобы не переписывать работающий CRUD ради проблемы, которая проявится позже.
Методы, выполняющие бамп, называются с суффиксом Local, чтобы разделение читалось из кода.

### Рассмотренные альтернативы
Бамп в репозитории — чище и тестируется без базы, но требует читать сущность перед записью либо
держать отдельные методы на каждое поле. Триггеры в SQLite — невидимы из кода, и отключить их
для pull сложнее, чем не вызывать метод.
