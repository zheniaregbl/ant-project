# 0007. navigation-compose вместо Navigation 3

### Дата
2026-10-05

### Статус
Принято, заменяет раннее решение использовать Navigation 3

### Контекст
Изначально выбор пал на Navigation 3 как на более новое решение с поддержкой всех таргетов
в Compose Multiplatform. При проработке экранов выяснилось, что документации и примеров под KMP
мало, а поведение back-стека на трёх платформах требует проверки вручную. Параллельно нужно было
решать задачи домена и UI, и навигация рисковала съесть непропорционально много времени.

### Решение
androidx navigation-compose 2.9.2 на весь проект. Один NavController и один NavHost на приложение,
фича-модули отдают наружу вложенный граф через extension на NavGraphBuilder. Типобезопасные роуты
через kotlinx-serialization, плагин сериализации подключается в каждом модуле, где объявлены роуты.

### Последствия
Поведение предсказуемо и задокументировано, примеров достаточно. Системный сигнал «назад» приходит
в одну точку на каждой платформе, мост между стеками писать не нужно. Переход на Navigation 3
позже возможен, потому что экраны не знают про навигацию и принимают лямбды. Остаётся на старом
API, который со временем будет получать меньше внимания.

### Рассмотренные альтернативы
Navigation 3 — новее, но на момент решения требовал бы собственных экспериментов вместо работы над
функциональностью. Decompose и Voyager — свои модели жизненного цикла, перестраивать архитектуру
ради них нет причины.
